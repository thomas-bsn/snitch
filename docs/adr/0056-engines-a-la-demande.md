# 0056 — Engines à la demande

Date : 2026-11-09. Statut : accepté. Spec parente : #368 ; ticket : #369. Complète l'ADR 0055 sans le supprimer.

## Contexte

L'ADR 0055 n'autorise l'exécution d'un moteur vocal non embarqué qu'à travers une Release d'engine signée : un éditeur de confiance signe un manifeste de roues avec son empreinte, le Super-administrateur l'importe, puis un Administrateur l'installe. Chaque adaptateur est écrit pour une Variante de modèle épinglée octet pour octet. Le registre est vide par défaut : l'onglet Engines affiche « No approved release matches » et un ordre de modèle échoue avec un message qui ne dit pas qu'un engine manque.

L'utilisateur est l'opérateur unique de sa propre installation. Il veut essayer les modèles qu'il découvre (Nemotron-3, TitaNet, ECAPA-TDNN, SepFormer, ResNet293-LM…) sans produire, signer et importer une enveloppe pour chacun, et sans qu'un modèle nouveau exige du code. La chaîne de signature protège contre un éditeur tiers qui n'existe pas ici : son coût est mal placé.

## Contradiction explicite avec l'ADR 0055

L'ADR 0055 pose qu'aucun code d'engine n'est exécuté sans avoir été approuvé par signature et figé par empreinte (« jamais d'exécution non validée »). Cette décision-ci la contredit pour le parcours par défaut : un engine à la demande est résolu par pip sur le Worker, sans signature, sans manifeste figé et sans empreinte connue à l'avance. L'ADR 0055 n'est pas abrogé : le parcours signé reste implémenté et utilisable, mais il passe sous un bloc « Avancé » réservé au propriétaire. Les termes Runtime approuvé, Release d'engine, Enveloppe de release et Variante de modèle épinglée restent valables pour lui. Le parcours par défaut n'est plus le parcours signé.

## Décision

- **Un engine est une famille de bibliothèque et une version.** Les familles supportées sont NeMo, SpeechBrain et WeSpeaker. Une table côté Snitch associe chaque famille à une bibliothèque, une version par défaut, les tâches couvertes (diarisation, empreinte, séparation) et ses contraintes de matériel. Un modèle du catalogue est rattaché à une famille.
- **Installation par pip dans un environnement virtuel isolé** par famille et par version, sous le volume des modèles. Plusieurs versions coexistent côte à côte sur un Worker, afin que deux modèles aux exigences différentes aient chacun la leur.
- **Le `pip freeze` de l'installation terminée est conservé** : il documente l'état exact des paquets résolus et sert de référence pour diagnostiquer ou revenir en arrière.
- **Un adaptateur par bibliothèque, pas par modèle.** Chaque adaptateur charge tout modèle de sa famille et respecte les contrats de sortie existants (tours de parole, vecteur normalisé). Ajouter une famille se limite à un adaptateur et une entrée de la table.
- **Garde-fous fixes, hors table et non désactivables par modèle** : aucun code de dépôt de modèle n'est exécuté (pas de code distant) ; les poids ne sont lus que dans un format sûr (pas de pickle exécutable) ; aucune configuration n'est lue comme du code ; aucun jeton Hugging Face ni hook de paquet n'est transmis aux installations de paquets. Un modèle qui exige du code distant est refusé avec une cause stable.
- **L'installation est proposée avec le modèle, après confirmation.** Choisir un modèle dont l'engine manque affiche, dans la même confirmation, l'engine, sa version, le disque et la durée estimés. Une fois confirmés, l'ordre d'engine puis l'ordre de modèle sont créés ensemble ; le modèle attend son engine. Un engine prêt ou en cours est réutilisé. Rien ne s'installe sans confirmation, et une reconnexion n'installe jamais rien.
- **Une famille non supportée est refusée avec un message distinct**, avant tout ordre, pour ne pas laisser croire à un problème d'environnement. Les causes d'échec d'installation (engine absent, paquet introuvable, résolution impossible, compilation échouée) sont aussi distinguées.
- **Séparation : l'engine est installable, la fonction reste désactivée.** L'engine SpeechBrain s'installe pour préparer la suite ; aucun adaptateur de séparation n'est livré et l'interface dit « engine installé, séparation pas encore disponible ». La décision de l'ADR 0055 sur la séparation inactive est inchangée.
- **Le reste du mécanisme est réutilisé** : contrôle du matériel avant tout ordre, ordres idempotents avec génération, inventaire et historique, annulation, nettoyage, désinstallation avec dépendances, mise à jour et retour arrière, inférence de test avant publication de la liaison, dispatch conditionné à l'inventaire. Les identités signée et canonique locale ne sont jamais confondues avec celle d'un engine à la demande.

## Mise en œuvre

- **Rattachement d'un modèle à une famille (#372).** Le catalogue porte une colonne `family`, vide par défaut. Vide : le contrat de l'ADR 0055 ne change pas (adaptateur embarqué sans engine, adaptateur signé avec Release). Renseignée : le modèle demande l'engine à la demande de cette famille, quel que soit le nom de son adaptateur ; c'est ce qui distingue Sortformer (adaptateur `nemo` embarqué, famille vide) d'un NeMo plus récent (adaptateur `nemo`, famille `nemo`). Une famille absente de la table de Snitch, ou qui ne couvre pas la tâche du modèle, est refusée (`unsupported_engine_family`) avant toute écriture. Un modèle ajouté depuis Hugging Face reçoit la famille de son adaptateur déduit (table `adapterFamily` : `nemo` et `nemo-titanet` vers NeMo, `speechbrain-ecapa` vers SpeechBrain, `wespeaker` vers WeSpeaker, adaptateur nouveau et sans version signée) ; pyannote et silero-jit restent embarqués et le Sortformer d'origine garde une famille vide. Le Worker accepte un ordre de modèle d'après la famille et la tâche de son runtime, pas d'après le nom d'adaptateur ; la séparation SpeechBrain n'a pas d'adaptateur actif et le catalogue ne peut pas contenir de modèle de séparation pris en charge, donc seul l'engine s'installe.
- **Modèles déjà au catalogue.** La migration 00140 remplit la famille des seules lignes dont l'adaptateur n'en désigne qu'une (`nemo-titanet` vers NeMo, `speechbrain-ecapa` vers SpeechBrain, `wespeaker`), sauf celles déjà exécutées sur une Release signée d'un Worker. Le Sortformer d'origine et toute ligne de diarisation `nemo` restent vides : rien n'indique si elles sont embarquées. Le Super-administrateur rattache ou détache un modèle existant par `PATCH /api/admin/voice-models/{id}` (`family`, vide pour détacher) ou depuis la modification de la référence, sans le supprimer ni le rajouter. La famille doit exister et couvrir la tâche du modèle ; un modèle à adaptateur embarqué (pyannote, silero-jit) n'en reçoit pas ; le changement est refusé (`voice_model_order_in_progress`) tant qu'un ordre ou une installation du modèle est ouvert. Le champ `signed_release_required` du modèle dit à l'interface si une Release signée est nécessaire : l'interface ne le déduit pas du nom d'adaptateur.
- **Un engine est une famille, une version et une tâche.** Une famille qui couvre plusieurs tâches (NeMo : diarisation et empreinte) donne une identité, une ligne de registre et un ordre par tâche ; l'ordre par famille accepte `kind`, la première tâche de la famille par défaut. Le dispatch d'un modèle de famille exige l'engine à la demande prêt de sa famille et de sa tâche.
- **Un répertoire par famille et version, partagé entre les tâches.** Sur le Worker, l'environnement est rangé sous le hachage de la famille et de la version, sans la tâche : les identités de Snitch de deux tâches d'une même version désignent le même répertoire. Une seconde tâche commandée sur un répertoire déjà installé le réutilise sans réinstaller et garde la même identité locale. Le répertoire n'est supprimé que si aucun modèle lié, quelle que soit la tâche, n'y est rattaché (le Worker a le dernier mot, `runtime_in_use`) ; Snitch refuse avant l'ordre (`engine_in_use`) en listant les modèles de toutes les tâches qui partagent le répertoire. Désinstaller une tâche d'un répertoire non lié retire donc aussi l'environnement de l'autre : son inventaire passe en échec `runtime_missing` au constat suivant.
- **Versions côte à côte, mise à jour et retour arrière (#376).** Chaque version d'une famille pour une tâche est une identité du registre, donc une ligne d'inventaire et un environnement propres ; un modèle reste lié à la sienne par `worker_model_runtime_bindings`. Règle retenue : *un seul ordre d'engine ouvert par Worker et par nom d'engine* (celui de la famille), quelle que soit la version. Deux versions coexistent une fois installées, mais s'installent l'une après l'autre : le refus `engine_order_in_progress` protège la machine contre deux `pip` lourds simultanés (#372). Une mise à jour (`POST /api/admin/voice-model-runtime-orders`, `version` à la place de `digest` pour un modèle de famille) vérifie que la cible est un engine à la demande de la famille et de la tâche du modèle (jamais une Release signée), l'enregistre si elle est nouvelle, puis réutilise l'ordre d'engine prêt ou en cours de ce Worker, sinon en crée un lié au même titre que l'installation d'un modèle : l'ordre de modèle attend l'engine, les poids ne sont jamais retéléchargés et la liaison reste sur l'ancienne version jusqu'à la réussite de l'inférence de test. Un retour arrière ne crée jamais d'ordre d'engine et refuse (`engine_not_installed`) une version absente ; le Worker échoue proprement (`runtime_incompatible`) si l'environnement a disparu entre-temps. La désinstallation reste celle de l'ADR 0055 (`engine_in_use` tant qu'un modèle est lié, modèles listés). Le remplacement d'un engine à la demande en échec passe par l'ordre de famille (même famille et même tâche, autre version).
- **Une seule source de la table des familles.** La table de Snitch (Go) fait foi. Le Worker en garde une copie pour installer et exécuter ; `scripts/check_engine_families.py` (exécuté par la CI) échoue si les familles, noms d'engine, distributions, tâches, tâches actives ou adaptateurs signés divergent. L'interface lit les familles et le champ `signed_release_required` de l'API et ne nomme aucun engine.
- **Migrations.** La migration 00138 (engines à la demande) est destructive à la descente : son `Down` supprime les lignes d'engines à la demande du registre et tout ce qui s'y rattache (liaisons de modèle, événements, ordres). La 00133 (remplissage des familles) n'est pas réversible : rien ne distingue une famille remplie d'une famille choisie.

## Alternatives écartées

- **Un adaptateur par modèle (variantes épinglées étendues).** C'est le modèle de l'ADR 0055 : sûr, mais tout modèle nouveau demande du code et une révision connue. Il contredit le but, essayer ce qu'on découvre, et multiplie le code à maintenir par un facteur égal au nombre de modèles.
- **Un registre signé embarqué dans Snitch.** Livrer des manifestes déjà signés supprimerait l'étape de signature pour l'opérateur, mais Snitch deviendrait l'éditeur : il faudrait auditer, signer et republier à chaque version de bibliothèque, et la clé serait celle du projet, non celle de l'opérateur. On échange une charge d'opérateur contre une charge de mainteneur, sans gain réel de confiance pour un opérateur unique.
- **Supprimer le parcours signé.** Rejeté : il reste utile à qui veut un chemin strict et reproductible, et il garde la valeur des Releases déjà importées.

## Conséquences

- **Reproductibilité perdue, assumée.** La version est résolue par pip au moment de l'installation : deux installations de la même famille et version peuvent résoudre des dépendances transitives différentes. Le `pip freeze` permet de diagnostiquer et de revenir en arrière, pas de garantir l'identique. Le parcours signé reste la voie reproductible.
- **Périmètre de confiance : l'opérateur seul.** Le choix de la famille, de la version et la confirmation reviennent à l'opérateur de sa propre installation. Ce modèle ne convient pas à une installation où des administrateurs peu fiables ordonnent des installations ; dans ce cas, le parcours signé reste la réponse.
- **Un environnement virtuel n'est pas une sandbox.** Il isole les dépendances, pas un paquet malveillant : celui-ci s'exécute avec les droits du Worker. Les garde-fous fixes réduisent la surface (code distant, pickle, jeton) mais ne la suppriment pas.
- **Dépendance au réseau et à l'index de paquets** à l'installation : disponibilité, compilation de sources et retraits de versions deviennent des causes d'échec visibles, non plus exclues par construction.
- **Deux parcours coexistent**, ce qui élargit la surface de test et de documentation ; l'interface doit rendre le parcours par défaut évident et reléguer l'import d'enveloppe sous « Avancé ».
- **Limites connues, décisions laissées au propriétaire.** (1) Un nouveau modèle NeMo ajouté depuis Hugging Face reçoit la famille de son adaptateur et passe donc à la demande par défaut, y compris un dérivé de Sortformer qui tournerait en embarqué : le choix du défaut reste à trancher. (2) Aucun contrôle de CUDA ni de VRAM n'est fait avant l'installation d'une famille à la demande (la table n'impose ni l'un ni l'autre) : un défaut de GPU ne se voit qu'à la vérification. (3) Une annulation pendant un `pip` en cours n'est prise en compte qu'à la fin de la commande en cours, jusqu'à 3600 s.
- Les moteurs embarqués (pyannote, NeMo embarqué, Silero), le modèle actif global et la transition d'empreintes de l'ADR 0044 ne changent pas.

## Addendum : versions récentes proposées

Le serveur Snitch lit l'index de paquets (`pypi.org`, hôte unique, nom de distribution tiré de la table des familles et jamais d'une requête) pour proposer, dans « Add an engine », les 10 dernières versions stables de la bibliothèque d'une famille. Les pré-versions, post-versions, versions de développement et versions retirées (yanked) sont écartées. La liste est mise en cache une heure ; en cas d'échec de l'index, la dernière liste connue est conservée et l'index n'est plus interrogé avant cinq minutes. Sans liste (index injoignable, première lecture), l'écran propose seulement la version par défaut et le champ reste libre. Choisir une version reste une décision de l'opérateur, confirmée avant tout ordre : une version proposée n'est jamais installée sans cette confirmation. Une version publiée ne garantit pas qu'un modèle donné fonctionne avec elle (Nemotron-3 exige un correctif de NeMo absent de la 3.0.0 publiée).

## Addendum : engine installé depuis un commit Git épinglé

Un modèle récent peut exiger un correctif de la bibliothèque qu'aucune version publiée ne contient encore (Nemotron-3 : NeMo 3.0.0 refuse l'attention « rope », corrigée sur la branche `main`). « Add an engine » propose donc, pour une famille dont la table nomme un dépôt, deux sources exclusives : une version officielle (ci-dessus) ou un commit Git.

- **Format.** La version d'un tel engine est `git-<commit complet de 40 caractères hexadécimaux minuscules>`. Le préfixe `git-` est réservé : une famille sans dépôt le refuse (`invalid_engine_order`), comme un commit abrégé, un nom de branche ou une URL. Aucun champ de manifeste n'est ajouté ; l'identité (famille, version, tâche) et le répertoire de l'environnement suivent la version comme pour une version publiée.
- **Dépôt fixe.** Le dépôt vient de la table de la famille, côté serveur (`GitURL`) et côté Worker (`FAMILIES[...]["git"]`), jamais de l'ordre : seule la famille NeMo l'a (`https://github.com/NVIDIA/NeMo.git`). Le Worker installe `nemo-toolkit[asr] @ git+<dépôt>@<commit>`, avec `GIT_TERMINAL_PROMPT=0`, et refuse l'engine si le `pip freeze` ne montre pas ce commit.
- **Image du Worker.** `pip` appelle `git` : l'image du Worker l'embarque désormais (paquet Debian épinglé, notice dans `deploy/NOTICES.md`). Un Worker dont l'image est antérieure échoue à l'étape `pip install` ; l'`stderr_tail` du journal porte « Cannot find command 'git' ». Il faut mettre à jour l'image.
- **Ce que cela ne garantit pas.** Un commit n'est pas une version publiée : ni reproductibilité de ses dépendances (`pip` résout au moment de l'installation), ni compatibilité avec un modèle donné. Le choix du commit reste une décision de l'opérateur, confirmée avant tout ordre, dans le périmètre de confiance décrit plus haut : un commit d'un dépôt amont n'est ni audité ni signé par Snitch.
